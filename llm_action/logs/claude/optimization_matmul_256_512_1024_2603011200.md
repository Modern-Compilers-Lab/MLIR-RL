## Key Findings

### Best Schedule: C15 = forall[4,32] + L2[4,16,64] + reg[4,4,64] + vec[4,4,64]
- **Time: 0.941 ms** → 312x speedup vs MLIR baseline, 0.506x vs PyTorch
- Produces `vector<4x4x64xf64>` = 1024 elements (at safety limit)
- 2048 parallel forall tasks (4×32 = 128 tiles per dimension → 128×16 tasks)

### Transform Code (C15):
```mlir
module attributes {transform.with_named_sequence} {
  transform.named_sequence @__transform_main(%arg0: !transform.any_op {transform.consumed}) {
    %matmul = transform.structured.match attributes{tag = "operation_0"} in %arg0
      : (!transform.any_op) -> !transform.any_op
    %tiled_parallel, %forall = transform.structured.tile_using_forall %matmul
      tile_sizes [4, 32]
      : (!transform.any_op) -> (!transform.any_op, !transform.any_op)
    %tiled_l2, %l2_loop0, %l2_loop1, %l2_loop2 = transform.structured.tile_using_for %tiled_parallel
      tile_sizes [4, 16, 64]
      : (!transform.any_op) -> (!transform.any_op, !transform.any_op, !transform.any_op, !transform.any_op)
    %tiled_reg, %r_loop0, %r_loop1, %r_loop2 = transform.structured.tile_using_for %tiled_l2
      tile_sizes [4, 4, 64]
      : (!transform.any_op) -> (!transform.any_op, !transform.any_op, !transform.any_op, !transform.any_op)
    transform.structured.vectorize %tiled_reg vector_sizes [4, 4, 64]
      : !transform.any_op
    transform.yield
  }
}
```

### Cache Working Set Analysis (C15):
- forall tile: M=4, N=32 (entire K=512 swept)
- L2 tile: A[4,64]=2KB, B[64,16]=8KB, C[4,16]=0.5KB → ~10.5KB per block (fits L1=32KB)
- Register tile: A[4,64]=2KB, B[64,4]=2KB, C[4,4]=128B → ~4.1KB register footprint
- OpenMP: 2048 tasks / 16 cores = 128 tasks per core

### Why Competitors Failed:
- **"dot" lowering (C21)**: Generates ub.poison requiring convert-ub-to-llvm; 5x slower than outerproduct path
- **Promote (C27)**: alloca-copy overhead ~320MB total for all L2 iterations → 5x slower
- **K-outer L2 (C32)**: B working set 64×32=16KB vs 8KB → tighter L1 fit, slightly worse
- **Skip L2 tiling (C24)**: No blocking → poor cache reuse, 1.48x slower than C15
- **4096 tasks (C34)**: OpenMP task scheduling overhead dominates, 9x slower
- **16 tasks (C25)**: Insufficient parallelism, 2.4x slower
- **Small K register tile (C30,C31)**: Too many loop iterations; vector<1x1x64> keeps K-reduction loop overhead high
- **innerreduction lowering (C28)**: Marginal change (0.973 vs 0.941 ms), no improvement over innerparallel

### Parameter Sensitivity:
- K register tile: Critical — 64 is optimal (full L2 K block), smaller loses throughput
- N_l2 = 16: Critical — keeps B block at 8KB (L1-friendly)
- forall[4,32] = 2048 tasks: Sweet spot — more (C34=4096→8.67ms) or fewer (C25=16→2.29ms) both worse
- M register tile = 4: Optimal — larger (8) causes vector size overflow, smaller loses efficiency

## Conclusion

The optimization converged to **C15** as the global optimum within the explored schedule space.
The schedule achieves **312x speedup** over MLIR baseline and **0.506x of PyTorch** performance,
coming within 2x of PyTorch on this f64 matmul kernel.

The key insight is the three-level tiling hierarchy (forall → L2 → register) with:
- Large K register tile (64) matching the L2 K-block size for full reuse
- N_l2=16 keeping the B working set L1-resident
- 2048 OpenMP tasks as the optimal parallelism grain

Further improvement would require: custom BLAS microkernel integration, NUMA-aware placement,
or software prefetching — all beyond the MLIR transform dialect's scope.
