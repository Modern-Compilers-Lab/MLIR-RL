### Phase 2 Notes
- **P2 EXEC FAIL**: parallel(28) on M=128 creates dynamic shapes (128/28 not divisible). Vectorization then produces `vector.mask` ops with multiple operations inside, which is invalid MLIR.
- **P5**: Parallelizing fine-grained inner tiles has extreme overhead (77ms vs 5.64ms baseline).
- **X1**: After vectorization, the `linalg.matmul` with tag is replaced by vector ops. No tagged operation remains, so all subsequent actions fail precondition.
- **Key insight**: Thread counts must evenly divide M=128 (use 4, 8, 16, 32, 64, 128) to avoid dynamic shapes.

### Phase 5 Notes
- **Key discovery 1: Wider vectorization matters.** vec(M,16,8) dramatically outperforms vec(4,4,4). Fully vectorizing the N-tile dimension (16) with K=8 reduction is optimal. K=16 causes register spilling (26.7x); K=4 is too narrow.
- **Key discovery 2: Extreme oversubscription works.** 128 threads on 28 cores gives the best result (46.4x), because each thread's tiny workload (1 row) has minimal per-thread memory footprint and excellent cache behavior.
- **Key discovery 3: N-tile must match vec N-size.** tile(1,32,64)->vec(1,16,8) is worse than tile(1,16,64)->vec(1,16,8) because the N-tile/vec mismatch creates an extra N-loop.
- **Less-explored actions (unroll, interchange, packing) do NOT improve performance** when inserted into the parallel->tile->vec pipeline. The overhead of extra loop nesting or modified access patterns outweighs any ILP benefit.
- vec(4,16,16) at product=1024 (max) is too wide — register spilling on Broadwell's 16 YMM registers. Sweet spot is product ~128-512 with K=8.

- **vec(1,64,4) is the new optimal vectorization for par(128)**: N=64 with K=4 (product=256) hits the sweet spot.

Legend:
- **OK**: Composition succeeds (both pre/post pass, executes correctly)
- **OK(dyn)**: Succeeds but creates dynamic tensor shapes
- **OK(bad)**: Succeeds but has terrible performance (e.g., tile->parallel = 77ms)
- **FAIL(pre)**: Second action's precondition fails (usually: tag lost)
- **FAIL(post)**: Second action's postcondition fails
- **FAIL(exec*)**: Precondition/postcondition pass but execution fails when thread count doesn't divide M. Works when num_threads divides M (requires tile in between for good results).
- **N/T**: Not tested

### Key Composability Rules
1. **Vectorization is a terminal action**: No action can follow vectorization (tag is lost).
2. **Parallelization must come first**: parallel->tile->vec works; tile->parallel is catastrophic.
3. **Thread count must divide M dimension**: Non-divisor counts create dynamic shapes that break vectorization at execution time.
4. **Packing doesn't compose well with vectorization**: 6D iterator space makes vector size product exceed limits or postconditions fail.

### Composability Issues Discovered
1. **Dynamic shape + vector.mask bug**: When parallelization creates dynamic tensor dimensions (thread count doesn't divide M), vectorization produces `vector.mask` ops with multiple operations inside. This is invalid MLIR and causes execution failure. **Workaround**: Only use thread counts that evenly divide the parallelized dimension.
2. **Packing + vectorization incompatibility**: Packing transforms `linalg.matmul` into a 6D `linalg.generic`. Vectorization with 6D vector sizes either exceeds the product limit (1024) or fails postcondition.
3. **Post-vectorization tag loss**: Vectorization replaces the tagged `linalg.matmul`/`linalg.generic` with vector ops, losing the `tag = "operation_0"` attribute. All subsequent action preconditions fail.
4. **tile -> parallel catastrophic overhead**: Parallelizing over fine-grained tiled iterations produces 77ms execution time (14x slower than baseline) due to thread scheduling overhead on tiny work units.

### Ordering Constraints
1. **Vectorization MUST be the last action** (terminal — no further tagged operations exist).
2. **Parallelization SHOULD be the first action** (tile->parallel has 14x overhead; parallel->tile is 29.7x speedup).
3. **Tiling should precede vectorization** to create appropriately-sized sub-problems for SIMD.
4. **Canonical pattern**: `parallel -> tile -> vec` (the HPC standard: coarse-grain parallelism -> cache blocking -> SIMD).

### Vectorization Width Guidance
- **With par(128) (1 row/thread)**: K=4 is optimal — matches AVX2 f64 lane width (4 doubles/register). N=64 minimizes loop iterations.
- **With par(16-64)**: K=8 is optimal — wider K amortizes loop overhead when tiles are larger.
- K=16+ causes register spilling on AVX2 (16 YMM regs). K=2 is too narrow.
- The vec product sweet spot is 128-512 (max allowed: 1024, but >512 spills registers).
- M_vec should match M per thread for full coverage (no M-loop overhead).
- N_vec must evenly divide N (128) to avoid dynamic shapes and masking overhead.

### RL Agent Guidance
- The action space is viable: all 6 actions apply, and the best schedule achieves **46.4x** speedup.
- The RL agent should learn the ordering constraint: parallel first, vec last.
- Thread count should be masked to divisors of M to avoid dynamic shape failures.
- **Oversubscription is beneficial**: 128 threads on 28 cores (4.6x oversubscribed) gives the best result.
- **Vectorization width matters**: vec(M,N,K) choice dramatically affects performance. vec(1,64,4) outperforms vec(4,4,4) by 5.6x.
- Less-explored actions (unroll, interchange, packing) do NOT improve over the pure parallel->vec pattern.
- **The simplest schedule wins**: parallel(128)->vec(1,64,4) uses only 2 actions and beats all 3+ action schedules.
- **K=4 optimal for AVX2 f64**: K-reduction size of 4 exactly matches AVX2 double-precision lane width.
