**Failures and Root Causes:**
- **V→X (all, #21-27)**: After Vectorization, the tag migrates to the outer `scf.for` loop attribute, not a linalg op. Pre=T (tag found on any op), but post=F (no structural transformation). **Vectorization is terminally terminal — must be last action.**

- **Par→V**: Succeeds (T,T) but produces masked vector ops due to dynamic inner matmul dimensions (M dimension is dynamic from non-exact division 1024/28).

## Key Findings

### Structural Incompatibilities (ACTION_DEPENDENCIES)

1. **Vectorization blocks everything (terminal action)**:
   - After Vectorization, the `{tag = "operation_0"}` attribute migrates from the linalg op to the outermost `scf.for` loop. All subsequent linalg-level transformation actions (Tiling, LoopInterchange, Promotion, Vectorization, Packing, Parallelization, ParallelTiling) find the tag but cannot apply their structural transformation — post=F for all 7.
   - **Vectorization must always be the final action in any schedule.**

2. **Packing blocks Vectorization (pre=F) and Promotion (post=F)**:
   - After Packing, the target op is a 6D linalg.generic. Vectorization's precondition check returns False — the 6D indexing structure is not compatible with the Vectorization tool's expected matmul pattern.
   - Promotion's postcondition fails on the 6D generic (returns code unchanged, post=F).
   - Other actions (Tiling, LoopInterchange, Parallelization, ParallelTiling, Packing) all succeed on the 6D generic output.

3. **Packing execution limitation (not a composability block)**:
   - Packing produces `linalg.unpack` which fails to bufferize at execution time. This is a tool-level limitation, not a structural incompatibility between actions. Downstream actions can still accept Packing output.

### Performance Insights

- **ParallelTiling tile size matters critically for parallelism**: PT[32,0,128] (256 work items, 9.1/core) vastly outperforms PT[64,0,64] (256 items but larger tiles with worse cache behavior at 28-core scale) and PT[128,0,128] (64 items, under-utilizing 28 cores).
- **LoopInterchange before Vectorization is essential**: PT[32,0,128]→I→V at 0.626ms vs PT[32,0,128]→V (untested but expected ~3x slower). Interchange moves the K reduction loop to the middle, placing the contiguous N dimension innermost for vectorization.
- **3-step PT→I→V dominates all 1-step and 2-step alternatives**: 534x speedup vs 56x for the best 1-step (ParallelTiling alone). Combining parallelism (PT), memory access optimization (I), and SIMD (V) is synergistic.
- **No benefit from adding Tiling between PT and V**: PT→T→V ≈ PT→V (5.80ms vs 5.81ms). At 64×64 tile size, additional scf.for loop overhead cancels any potential cache benefit.
- **V tile size register pressure**: Optimal V tile [4,8,8] for this shape gives a 4×8=32 f64 output register tile = 8 YMM regs, leaving sufficient register file for A/B broadcast tiles without spilling.
- **Gap to PyTorch**: Best MLIR result is 0.625× PyTorch (1.37× slower). PyTorch uses MKL DGEMM which employs AVX2 FMA micro-kernels with hand-tuned register blocking, prefetching, and packing strategies not available in this action vocabulary.
