### Cross-Kernel Observations

1. **VP alone** is the simplest and most robust schedule. Best for small-medium kernels (35-191x speedup). For large kernels it still achieves 222x but is outperformed by PT-prefixed schedules.

2. **ParallelizationTiling → VectorizationSequential** (PT→VS) is the best 2-step schedule for medium-large kernels. PT distributes work across threads via scf.forall over parallel dims, then VS vectorizes the inner loop with scf.for + vector ops. VS outperforms VP as a terminal action when preceded by PT.

3. **ParallelizationThreads → VectorizationSequential** (PTh→VS) is best for small kernels. PTh's 1D thread distribution is more efficient for small matrices where 2D tiling (PT) creates too many small tiles.

4. **ParallelizationTiling → Tiling → VectorizationSequential** (PT→Tile→VS) adds cache-friendly tiling between parallelization and vectorization. Best for large kernels where the per-thread tile is still large enough to benefit from cache blocking.

5. **ParallelizationTiling → LoopInterchange → VectorizationParallel** (PT→LI→VP) is a strong alternative that reorders loops for better data access patterns before parallel vectorization. Consistently in top-3 for medium/large kernels.

6. **Tiling alone (without parallelization) is always harmful**: Pure Tile → VP is barely better than baseline, and Tile → Tile → VP is catastrophically worse (62-7000x slower than baseline). Sequential tiling without thread distribution wastes available parallelism.

7. **Schedule length vs performance**: For small kernels, 1-2 step schedules dominate. For large kernels, 2-3 step schedules with PT as prefix provide the most benefit. 4+ step schedules showed diminishing returns across all sizes.

## Key Findings

### Best Schedules by Kernel Size
- **Small matmuls**: PTh → VS (0.133ms, 37.5x) or VP alone (0.141ms, 35.3x)
- **Medium matmuls**: VP alone (0.433ms, 191x) or PT → Tile → VS (0.558ms, 148.5x)
- **Large matmuls**: PT → Tile → VS (2.49ms, 272x) or PT → VS (2.50ms, 272x)

### Composability Issues Discovered
- VectorizationSequential and VectorizationParallel consume the linalg op and move the tag to a loop construct. All subsequent actions pass precondition (tag is found) but fail postcondition (transformation doesn't produce valid output). This makes VS/VP structurally terminal.
- No precondition failures were observed for any pair, indicating robust tag matching.

### Ordering Constraints
- VS and VP must be the **last** action in any schedule (terminal).
- Parallelization (PT or PTh) should come **before** Tiling for best results.
- LoopInterchange adds value primarily **after** ParallelizationTiling, not before it.
- Tiling without prior parallelization is always harmful.
