## Phase 2: Pairwise Compositions

All 36 ordered pairs tested via actual tool invocations.

### Composability Matrix

|--------------|--------|-----|--------|--------|-----|-----|

| LI | OK | OK | OK | OK | OK | OK |
| VecSeq | FAIL(post) | FAIL(post) | FAIL(post) | FAIL(post) | FAIL(post) | FAIL(post) |
| VecPar | FAIL(post) | FAIL(post) | FAIL(post) | FAIL(post) | FAIL(post) | FAIL(post) |
| PT | OK | OK | OK | OK | OK | OK |
| PTh | OK | OK | OK | OK | OK | OK |

**Structural findings:**
- **VecSeq and VecPar are strictly terminal**: They consume the linalg.generic and replace it with vector ops. The tag moves to the enclosing scf loop. All subsequent actions pass precondition (they find the tag) but fail postcondition (the matched op is no longer linalg-level). The code is returned unchanged.
- **Tiling, LI, PT, PTh compose freely**: They preserve the linalg.generic with its tag, allowing any subsequent action to match and transform it. Multi-level tiling, interchange-then-tile, parallel-then-tile, etc. all work.
- **No block edges besides VecSeq/VecPar terminal behavior**: All non-vectorization actions compose cleanly in any order.

### Dependency edges (block rules):
- VectorizationSequential -> [Tiling, LoopInterchange, VectorizationSequential, VectorizationParallel, ParallelizationTiling, ParallelizationThreads]
- VectorizationParallel -> [Tiling, LoopInterchange, VectorizationSequential, VectorizationParallel, ParallelizationTiling, ParallelizationThreads]

## Phase 4: Best Schedule per Kernel Subset

| Subset | Kernel | Best Schedule Shape | Time (ms) | vs Base | vs PyTorch |
|--------|--------|-------------------|-----------|---------|------------|
| 2D small | relu_128_1024 | (none - base wins) | 0.110 | 1.0x | 1.09x |
| 4D medium | relu_128_64_56_56 | [VectorizationParallel] | 5.31 | 6.05x | 1.18x |
| 4D large | relu_128_240_130_130 | [VectorizationParallel] | 122.0 | 5.42x | 0.96x |

**Recommended schedule shapes for relu family (ranked by generality):**

1. **`[VectorizationParallel]`** — Universal best. Wins or ties on all subsets ≥ medium size. Combines parallelization (forall) + vectorization in one action. Simple, robust, no parameter sensitivity beyond vector sizes matching dim divisibility.

2. **`[ParallelizationThreads, VectorizationParallel]`** — Runner-up. Best for small 2D kernels where explicit thread control before vectorization helps. Marginal overhead on larger kernels.

3. **`[Tiling, VectorizationParallel]`** — Third place. Tiling before vectorization can help with cache locality on very large tensors but adds overhead. Close to VecPar alone.

4. **`[LoopInterchange, VectorizationParallel]`** — Tied with VecPar on medium kernels. Interchange is a no-cost structural rewrite that can improve access patterns.

5. **`[ParallelizationThreads, Tiling, VectorizationParallel]`** — 3-step schedule. Useful when both parallelism and cache tiling matter, but overhead often negates gains for ReLU.

## Key Findings

### 1. Composability Structure
- **Terminal actions**: VectorizationSequential and VectorizationParallel consume the linalg.generic op. No further actions can compose after them. This is the ONLY structural constraint.
- **Free composition**: Tiling, LoopInterchange, ParallelizationTiling, and ParallelizationThreads compose freely in any order and any depth.
- **Implication**: All valid schedule shapes are of the form `[prep_actions...] + [VecSeq | VecPar]` where prep_actions ∈ {Tiling, LI, PT, PTh}*.

### 2. VectorizationParallel Dominance
- VecPar is the single most impactful action, providing 5-6x speedup over base MLIR on medium-large kernels.
- It combines `forall` parallelization + SIMD vectorization in one step — getting both parallelism and vectorization for free.
- Additional prep steps (tiling, interchange, thread distribution) rarely improve over VecPar alone.

### 3. Kernel Size Sensitivity
- **Small kernels** (< 200K elements): Transformation overhead dominates. Base MLIR is already near PyTorch. No schedule helps.
- **Medium kernels** (25M elements): VecPar achieves 1.18x PyTorch speedup. Sweet spot for single-action optimization.
- **Large kernels** (520M elements): VecPar achieves 0.96x PyTorch (near parity). Vectorization width limited by dim divisibility.

### 4. Divisibility Constraints
- Vector/tile sizes MUST exactly divide loop bounds. Dims like 130 (= 2*5*13) severely limit valid parameter choices.
- This is a parameter-level concern, not a schedule-shape concern. All shapes work structurally regardless of dims.

### 5. VecSeq vs VecPar
- VectorizationSequential provides NO speedup (1.0x) — it vectorizes but doesn't parallelize.
- VectorizationParallel provides 6.0x speedup — it does both.
- For ReLU (all-parallel iterators), VecPar strictly dominates VecSeq. VecSeq should be excluded from relu schedule graphs.
