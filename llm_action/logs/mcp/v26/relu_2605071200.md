## Key Insights

1. **ReLU is memory-bandwidth bound**, not compute bound. The operation per element (compare + select) is trivial compared to memory access time.

2. **Parallelization is the only meaningful optimization for large kernels.** It enables multi-threaded memory access, which is the bottleneck.

3. **Vectorization hurts ReLU performance** because:
   - The vector loop nest adds iteration overhead (tensor.extract_slice, vector.transfer_read/write per tile)
   - The computation per tile is too simple to amortize the overhead
   - The compiler's auto-vectorization likely already handles the simple ReLU pattern

4. **Small 2D kernels (131K elements) are already optimal** -- only constant hoisting via canonicalization provides marginal benefit.

5. **Tile size for parallelization matters**: [4,0,0] or [8,0,0] (splitting batch dim) works well; [4,4,0] (splitting two dims) creates too many tasks.

6. **Best universal ReLU strategy**:
   - Small kernels (<1M elements): canonicalization only
   - Large kernels (>10M elements): tiling_based_parallelization on batch dimension with tile_size=4 or 8
