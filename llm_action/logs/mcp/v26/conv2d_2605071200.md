## Key Insights

1. **Parallelization dominates**: For all 4 conv2d kernels, `tiling_based_parallelization [4,4,0]` provides the best speedup (25-28x). This tiles along the N (batch) and F (filter) dimensions, creating 32*48/64/8 parallel tiles.

2. **Im2col is NOT beneficial for conv2d**: Despite converting conv2d to matmul-like operations, im2col adds overhead:
   - For 1x1 kernels: neutral to slightly worse
   - For 3x3 kernels: significantly worse (3x slower due to expanded 1152-wide reduction)
   - After parallelization: im2col adds overhead vs pure parallel

3. **Vectorization fails on conv2d**: Direct vectorization of conv2d consistently fails postcondition. It needs prior tiling to create appropriately-sized tiles, but even then fails.

4. **Composition difficulty**: Most second-stage actions fail postcondition after im2col. The linalg.generic ops produced by im2col are harder to further optimize.

5. **Tiling alone is insufficient**: Without parallelization, tiling provides < 2% improvement. The loop overhead is negligible for these large tensors.

6. **thread_count_parallelization vs tiling_based_parallelization**: Both achieve similar results (~25x), but tiling-based is slightly better because it parallelizes across two dimensions (N and F) giving more parallel work units.

7. **Optimal strategy for conv2d**: Apply `tiling_based_parallelization` with tile sizes that create enough parallel work for all 28 cores. The [4,4,0] configuration creates 32*48 = 1536 (K1), 32*64 = 2048 (K2/K3), or 64*8 = 512 (K4) parallel tiles.
