Key structural finding: **Vectorization is a terminal action.** Once vectorization runs, the linalg op with the tag is replaced by vector.transfer_read/write + arith ops. No subsequent action can find the tagged operation.

**Promotion is NOT terminal.** It converts tensor->memref but preserves the tagged `linalg.matmul` op. Tiling, Vectorization, Parallelization, and LoopInterchange all pass pre/post conditions after Promotion.

## Key Findings

### Best Schedule
- Schedule: `parallelization(num_threads=16) -> tiling(tile_sizes=[4,16,32]) -> vectorization(vector_sizes=[4,16,4])`
- Time: 0.130 ms
- Speedup: 60.2x vs MLIR base, 0.71x vs PyTorch

### Runner-up (simpler 2-step)
- Schedule: `parallelization(num_threads=16) -> vectorization(vector_sizes=[8,8,8])`
- Time: 0.138 ms
- Speedup: 56.6x vs MLIR base, 0.67x vs PyTorch

### Composability Issues Discovered
- **Vectorization is terminal**: After vectorization, the linalg.matmul with `tag = "operation_0"` no longer exists. It is replaced by vector transfer reads, arith.mulf, vector.multi_reduction, and vector transfer writes. All subsequent actions fail precondition because they cannot find the tagged op.
- **Promotion is NOT terminal**: Converts tensor->memref but preserves the tagged `linalg.matmul`. Tiling, Vectorization, Parallelization, and LoopInterchange all compose after Promotion.
- **Vectorization product constraint**: vector_sizes product must be <= 1024. Tiling to 16x16x16 then trying vec(16,16,16) = 4096 fails precondition.
- **Interchange converts matmul to linalg.generic**: This preserves the tag and allows subsequent vectorization/tiling, but changes iteration order.

### Ordering Constraints
- Vectorization MUST come last in any schedule (terminal)
- Promotion can appear anywhere before Vectorization (not terminal; preserves tagged op)
- Parallelization should come BEFORE tiling (outer parallelism wraps inner tiled loops)
- Tiling should come BEFORE vectorization (creates appropriately sized tiles for vector ops)
- Preferred canonical order: Parallelization -> [Promotion] -> Tiling -> Vectorization

### Hardware Observations
- 16 threads optimal for this 128-row matrix (8 rows per thread = good cache utilization)
- 32 threads slightly worse (4 rows per thread = too fine-grained, overhead)
- Vector sizes [8,8,8] (product=512) give best single-action vectorization for f64 on AVX2
- Tile sizes [4,16,32] with vec [4,16,4] optimizes for: M=4 rows in registers, N=16 columns (2 AVX2 vectors of f64), K=4 for reduction
