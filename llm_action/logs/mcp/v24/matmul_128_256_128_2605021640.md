### Phase 2 Summary
- **Most composable**: Tiling, Parallelization (all 9 successors OK)
- **Least composable**: Vectorization (only Canonicalization succeeds after it; effectively terminal)
- **Structural blockers identified**:
  - Vectorization: replaces linalg.matmul with vector ops; tag moves to scf.for; blocks all linalg-targeting actions
  - Promotion: bufferizes tensor->memref; blocks Packing (tensor-only) and Canonicalization
  - Packing: reshapes to 6-dim linalg.generic; blocks Vectorization (precondition rejects packed form)

## Phase 4: Key Findings and Ordering Constraints

### Ordering Constraints (documented but NOT encoded as block edges)
1. Vectorization must be the last linalg-targeting action in any schedule
2. Promotion should come before Tiling/Interchange for cache optimization, but after Parallelization
3. LoopInterchange[0,2,1] (swap K and N) significantly improves data locality for column-major access

### Performance Insights
1. Single actions: Parallelization(32) gives best single-action speedup (13.64x)
2. Vectorization[4,4,4] is the only working vectorization config (sizes >= 16 fail pre)
3. LoopInterchange[1,0,2] is the only interchange that hurts performance (0.91x)
4. Multi-step: Combining Parallelization + Tiling + Vectorization achieves 38.7x vs MLIR base
5. Gap to PyTorch (0.093ms) remains at ~1.7x, likely due to PyTorch's optimized BLAS backend

### Structural Observations
- After Vectorization: tag attribute moves from linalg.matmul to scf.for; all subsequent linalg transforms lose their payload op
- After Promotion: IR transitions from tensor to memref semantics; tensor-only transforms (Packing) become invalid
- After Packing: matmul becomes 6-dim linalg.generic with inner block dimensions; Vectorization precondition rejects this form
- Canonicalization on clean matmul (or interchanged generic) is a no-op (post=F); it only succeeds when prior transforms introduce simplification opportunities
