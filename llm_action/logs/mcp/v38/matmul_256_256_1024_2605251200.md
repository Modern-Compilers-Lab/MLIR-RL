### Phase 2 Key Observations
- **Terminal actions:** Vectorization and ParallelVectorization are terminal — after either is applied, ALL subsequent actions pass precondition but fail postcondition. This is because vectorization moves the `tag` from the `linalg` op to the outer `scf.for`/`scf.forall` loop, making the code invalid for further linalg-level transforms.
- **Fully composable actions:** Tiling, LoopInterchange, Promotion, LoopUnrolling, TilingBasedParallelization, and DirectParallelization compose freely with all 8 actions (including themselves).
- **Ordering constraint:** Vectorization/ParallelVectorization must always be the LAST action in any schedule.

## Phase 3: Multi-step Schedules
Promising 2-step combinations executed and measured:

| # | Schedule | Time (ms) | Speedup vs base | vs PyTorch |
|---|----------|-----------|-----------------|------------|
| M1 | LoopInterchange[0,2,1] → ParallelVec[8,16,4] | 0.79 | 218x | 0.40x |
| M2 | Tiling[32,32,32] → ParallelVec[8,16,4] | 155.38 | 1.1x | 0.002x |
| M3 | TilingBasedParallel[8,32,0] → Vectorization[8,16,4] | 1.00 | 172x | 0.31x |

### Phase 3 Key Observations
- **LoopInterchange → ParallelVectorization** is the strongest combination, achieving 0.79 ms (218x vs base). The interchange reorders loops to [i,k,j] improving memory access for the j-dimension (size 1024), which ParallelVectorization then exploits with parallel tiling + SIMD.
- **Tiling → ParallelVectorization** actually degraded performance (155 ms) — tiling overhead on already-small tiles creates many loop nests that vectorization cannot efficiently parallelize.
- **TilingBasedParallel → Vectorization** achieves 1.00 ms — coarse-grained parallelism + sequential vectorization is effective but slightly worse than the IntC → PVec combination.

## Phase 4: Local Tuning
Tuned the best schedule (LoopInterchange[0,2,1] → ParallelVectorization) by varying vector sizes:

| # | Vector Sizes | Time (ms) | Speedup vs base | vs PyTorch |
|---|-------------|-----------|-----------------|------------|
| T1 | [8,16,4] | 0.79 | 218x | 0.40x |
| T2 | [4,4,4] | 0.72 | 239x | 0.43x |
| T3 | [16,16,4] | 1.43 | 121x | 0.22x |
| T4 | [4,16,8] | **0.50** | **344x** | **0.62x** |

### Phase 4 Key Observations
- **Best overall schedule: LoopInterchange[0,2,1] → ParallelVectorization[4,16,8]** at 0.50 ms (344x speedup vs MLIR base, 0.62x of PyTorch)
- Vector sizes [4,16,8] work best: small parallel tile on i (4), large on j (16) to exploit the wide j-dimension (1024), and moderate on k (8) for the reduction dimension (256).
- Larger vector sizes [16,16,4] hurt performance — likely exceeding register pressure on Broadwell AVX2 (256-bit vectors, 16 YMM registers).
- Even the best MLIR schedule reaches only 62% of PyTorch performance, which uses highly optimized BLAS (MKL/OpenBLAS) with architecture-specific microkernel implementations.

### Composability Summary
- **Terminal actions (must be last):** Vectorization, ParallelVectorization
- **Freely composable:** Tiling, LoopInterchange, Promotion, LoopUnrolling, TilingBasedParallelization, DirectParallelization
- **Optimal ordering pattern:** Data layout transforms (LoopInterchange) → Parallelism (TilingBasedParallel/DirectParallel) → Vectorization (Vec/ParallelVec as final step)

### Performance Hierarchy (single actions)
1. ParallelVectorization: ~130x (parallelism + SIMD in one step)

3. LoopInterchange [0,2,1]: ~9x (memory access optimization)
