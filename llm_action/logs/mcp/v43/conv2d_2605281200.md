## Phase 4: Schedule Selection (revised after Phase 5)

### Best Shape per Kernel Category

| Category | Kernel | Best Shape | Time (ms) | Speedup vs base |
|----------|--------|-----------|-----------|----------------|
| Medium 3x3 | K1 | **ParTiling → Tiling → Promotion** | 11.40 | 37.39x |
| Small 1x1 pointwise | K2 | ParTiling → Tiling → VecPar | 0.42 | 32.68x |
| Large 1x1 pointwise | K3 | **ParTiling → Tiling → Promotion** | 15.14 | 49.52x |

### Selected Schedule Paths for SCHEDULE_GRAPH

1. **ParTiling → Tiling → Promotion** — new top performer for medium/large kernels. Promotion copies tiled operands to contiguous stack buffers, giving the lowering pipeline better data locality. Beats VecPar-based paths by 2-2.3x on K1/K3.
2. **ParTiling → Tiling → VecPar** — best for small kernels where VecPar's SIMD wins over promotion copy overhead.
3. **Im2col → ParTiling → VecPar** — alternative for large 1x1 pointwise. Converts to batched matmul-like generic.
4. **ParTiling → VecPar** — simpler 2-step fallback. Useful when tiling parameters are hard to find (e.g. odd spatial dims).
5. **ParTiling → Tiling → Tiling → VecPar** — deeper tiling variant, giving RL more parameter tuning flexibility.

### Excluded Shapes (rationale)

- **VecPar alone** (9.97x on K1) — much weaker than any multi-step schedule with parallelization
- **ParTiling alone** (27.47x on K1) — strong but PT→T→Promo (37.39x) is strictly better
- **LoopInterchange paths** — LI blocks ALL vectorization (VecPar AND VecSeq, even with intermediate tiling). Not competitive.
- **Packing paths** — block VecPar; would need alternative terminal. Not tested, unlikely to beat Promotion path.
- **Im2col → VecPar** — nearly identical to Im2col→PT→VP. PT step is redundant since VecPar creates own forall.

### Root Cause: Why K1/K3 Cannot Beat PyTorch

The 4-6x performance gap for K1 and K3 is fundamentally due to **spatial dimension misalignment with SIMD widths**:

1. **K2 succeeds because OH=OW=4**: VP creates vector<4x4x4x4x4x1x1> with all parallel dims divisible by 4, yielding efficient forall(1,1,1,1,C/4)=clean vectorized computation.

2. **K1 fails because OH=OW=3**: VP must use vector_size=1 for spatial dims, creating forall(1,2,3,N_outer)=many fine-grained tasks with tiny vectors (vector<4x4x1x1>). Only 16 FLOPs per task vs scheduling overhead.

3. **K3 fails because OH=OW=7**: Same problem — 7 is not divisible by 2 or 4. VP creates forall(1,2,7,7)=98 inner tasks with vector<4x4x1x1>, each doing only 16 FLOPs.

4. **Promo helps cache but not compute**: Promotion gives L1 cache locality (~19KB working set fits 32KB L1), but computation remains scalar. PyTorch uses MKL-DNN's hand-optimized AVX2 kernels with register blocking and masked loads.

### What Would Close the Gap

Extensions needed beyond the current v43 action set:
- **Masked vectorization**: VP with padding/masking for non-aligned spatial dimensions (e.g., pad OH=7→8 and mask the last element)
- **Register blocking**: Larger vector tiles (e.g., 8x8 output blocks using multiple AVX2 registers simultaneously)
- **Fused im2col+compute**: Inline the im2col data extraction into the compute kernel to avoid materializing intermediate tensors
