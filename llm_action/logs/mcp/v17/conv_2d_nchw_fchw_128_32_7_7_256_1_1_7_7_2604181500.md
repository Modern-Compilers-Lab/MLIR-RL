### Second Best Schedule

### Composability Issues Discovered
1. **vectorization after tiling fails precondition**: Tiling produces `linalg.conv_2d_nchw_fchw` with smaller tensors, but vectorization cannot find the operation tag after tiling has been applied.
2. **vectorization fails at runtime on img2col output**: Both `vec[4,4,4,4,4,1,1]` on conv and `vec[4,16,4,4]` on img2col output produce valid IR (pre+post pass) but the `vector.mask` op generates invalid lowered MLIR that cannot be parsed by the execution backend. This is a consistent vectorization lowering bug.
3. **tiling -> parallel on small tiles is catastrophic**: Parallelizing over a dimension of size 4 with 32 threads creates massive overhead (612 ms vs 41 ms base).
4. **promotion adds harmful padding overhead**: On the parallel+img2col code, promotion[0,1] increases time from 1.20 to 11.75 ms (9.8x slower).
5. **loop interchange on img2col matmul hurts**: Permutation [0,2,1,3] (swap filter/spatial) increases time from 1.20 to 2.92 ms. Original order is cache-optimal.

### Ordering Constraints
1. **Parallelization should come FIRST**: `parallel -> kernel_lowering` (1.20ms) >> `kernel_lowering -> parallel` (1.48ms). Pre-parallelizing partitions the batch dimension before any further transforms.
2. **kernel_lowering (img2col) enables efficient tiling**: Converts 7-loop conv into 4-loop batched matmul, enabling fine-grained tiling with much better performance.
3. **Small tiles are optimal for the matmul**: [0,4,0,4] or [0,8,0,4] beat larger tiles. The reduction dim (K=32) should be tiled small (4) not consumed whole (32).
4. **Unrolling provides marginal benefit**: unroll(4) on the tiled code gives ~0.01ms improvement (1.07 -> 1.06 ms).
5. **32 threads > 16 threads** even on 28-core machine: Extra threads help hide memory latency.

### Tiling Guidelines for img2col Matmul
- **Filter dimension (d1=256)**: Tile 4-8 is optimal. Larger tiles (16, 32) slightly worse.
- **Reduction dimension (d3=32)**: Tile 4 is optimal. Full reduction (32) is 16% slower.
- **Batch dimension (d0=4 per thread)**: Don't tile further; already small enough.
- **Spatial dimension (d2=49)**: Don't tile; it's the innermost parallel dim and untiled access is fine.
- **Cache analysis**: 4x4 filter tile + 4x4 reduction = 16+784+784 = 1584 doubles (~12KB), fits L1d (32KB).

### Performance Gap to PyTorch
- Best MLIR schedule: 1.064 ms
- PyTorch JIT: 0.29 ms
- Gap: ~3.7x. PyTorch likely benefits from: optimized BLAS (MKL/OpenBLAS), AVX2 intrinsics, better memory layout, and more aggressive vectorization that our current vectorization action cannot achieve due to lowering bugs.

## Phase 6: Vectorization Debugging

### Root Cause: `vector.mask` Multi-Op Wrapping

**Error**: `'vector.mask' op expects only one operation to mask`

**Mechanism**:
1. The vectorization action tiles with `tile_using_for` then vectorizes with `transform.structured.vectorize` using the same sizes.
2. When tile sizes don't evenly divide dimensions (e.g., d2=49 / tile=4 → 12 full tiles + 1 remainder tile of size 1), the last tile is `tensor<...x?xT>` (dynamic size).
3. Vectorizing dynamic-sized tiles with explicit `vector_sizes` generates `vector.mask` ops to handle the partial vector.
4. The `vector.mask` wraps the entire reduction body (mulf + addf + multi_reduction + scf.for loops + vector.insert chains = ~100 ops), violating the single-op constraint.
5. The lowering pipeline (`convert-vector-to-llvm{enable-x86vector}`) can't parse this invalid IR.

**Affected dimensions for this kernel**:
- d2=49 (spatial, 7x7 collapsed): NOT divisible by any VOCAB value [2, 4, 8, 16]
- d0=128, d1=256, d3=32: All powers of 2, divisible by all VOCAB values

### Fix: Tile → Pad → Vectorize

**Solution**: Insert `transform.structured.pad` between tiling and vectorization.
- Padding converts `tensor<...x?xT>` → `tensor<...xNxT>` (static) for remainder tiles
- Eliminates `vector.mask` generation entirely
- Standard MLIR pattern: tile → pad → vectorize

**Implementation**: Updated `vectorization.py` to generate:
```mlir
%tiled_op, %loops:N = transform.structured.tile_using_for %op tile_sizes [...]
%padded, %pad, %copy = transform.structured.pad %tiled_op
    {padding_values = [0.0 : f64, ...], padding_dimensions = [0, 1, ..., N-1]}
transform.structured.vectorize %padded vector_sizes [...]
```

### Key Insight: Vectorization Not Beneficial Here

**Why vectorization doesn't help this kernel**:
1. **Non-power-of-2 spatial dim (49=7x7)**: Forces either padding (slow) or skipping d2 vectorization (limited benefit)
2. **Small tile overhead**: Tiling all 4 dims with sizes [1,4,4,4] creates 4 nested loops with 26K+ iterations per thread. Loop overhead dominates vector benefit.
3. **Padding overhead**: `tensor.pad` creates dynamic allocations inside tight loops. Even though most iterations have pad_amount=0, the dynamic check can't be statically folded.
4. **Already memory-bound**: With parallelization, the computation is memory-bound. Vectorization improves compute throughput but doesn't help memory-bound workloads.

### Knowledge Base Entry for Action Generation

**Rule: Vectorization requires tile → pad → vectorize pattern**
- **Trigger**: When `transform.structured.vectorize` is used with explicit `vector_sizes` on tiled code.
- **Reason**: `tile_using_for` produces dynamic-sized remainder tiles when dim % tile_size != 0. Direct vectorization of dynamic tiles generates `vector.mask` ops wrapping multiple operations, causing `'vector.mask' op expects only one operation to mask` lowering failure.
- **Fix**: Always insert `transform.structured.pad` between tiling and vectorization. Padding values should be zero in the element type (e.g., `0.0 : f64`). `padding_dimensions` should cover all tiled dimensions.
- **Performance caveat**: Padding adds overhead (~10-20x slowdown in tested cases). Vectorization is most effective when:
  - All dimensions are divisible by vector sizes (no actual padding needed)
  - Tile sizes are large enough to amortize loop overhead
  - The workload is compute-bound, not memory-bound
- **Alternative**: Only use vector sizes that evenly divide the corresponding dimension sizes. This avoids masking entirely but limits the parameter space.
