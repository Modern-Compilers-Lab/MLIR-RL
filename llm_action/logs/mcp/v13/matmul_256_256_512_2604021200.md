### Composability Issues Discovered
- **tile -> parallel creates catastrophic overhead**: Parallelizing inside tiled loops spawns threads for tiny matmul tiles, 613.88 ms (7.2x worse than base)
- **vectorization [16,16,16] on full kernel or 16x16 tiles fails precondition**: Vector sizes must be <= tile/tensor dimensions
- **fusion -> unrolling fails postcondition**: Unrolling is incompatible after fusion
- **fusion -> peeling fails postcondition**: Peeling is incompatible after fusion
- **packing + vectorization is fundamentally incompatible**: Packing creates 6D generic op, vectorizer expects 3D
- **fusion -> promotion -> vec works but terrible perf**: nofold padding overhead (1.929 ms)
- **pad(32) doubles tiles, wasting computation**: 1.702 ms vs 0.327 ms with pad(8)
- **Padding AFTER tiling is catastrophic**: 2.574 ms vs 0.338 ms when padding comes first

### Ordering Constraints
- **Parallelization MUST precede tiling** — never the reverse (7.2x slowdown if reversed)
- **Vectorization should be the last action** — it operates on the innermost loop body
- **Padding MUST precede tiling** — padding after tiling creates overhead around each micro-tile (7.6x worse)
- **Fusion subsumes parallelization + tiling** — fusion creates parallel tiled structure in one step, most effective single action
- **Fusion + padding + vectorization is the strongest 3-step pattern** — padding before vec provides ~15% improvement
- **Interchange after fusion/padding is neutral or harmful** — doesn't help when combined with padding
- **Asymmetric fusion tiles (larger N) beat symmetric** — fusion(16,32,16) > fusion(16,16,16)

### Performance Gap to PyTorch
- Best MLIR schedule (0.327 ms) is ~1.69x slower than PyTorch JIT (0.194 ms)
- This is a significant improvement from the initial 2.2x gap (0.422 ms) after Phase 4
- PyTorch likely uses optimized BLAS (MKL/OpenBLAS) with hand-tuned AVX2 microkernels
- To close the remaining gap, would need: microkernel-level register tiling, software pipelining, and/or cache-line-aligned memory access patterns — beyond current action space capabilities

### Ordering Constraints (Complete)
- **Vectorization MUST be last**: All subsequent actions fail precondition
- **Parallelization MUST precede tiling**: Never reverse (7.2x slowdown)
- **Padding MUST precede tiling**: After tiling = 7.6x worse

- **Padding should immediately precede vectorization**: fusion->pad->vec is the optimal pattern
- **Interchange is neutral or harmful** after fusion/padding
- **Promotion before fusion is slightly better than after**: Full-matrix nofold copies (1.156 ms) vs per-tile copies (1.414 ms)

### 11b. Promotion (nofold padding)
| # | Schedule | Time (ms) | Speedup | Speedup to PyTorch |
|---|----------|-----------|---------|--------------------|
| M4 | tile(32,32,32)->promotion(8)->vec(4,8,8) | 20.018 | 4.23x | 0.010x |

**Promotion observations:**
- Promotion ALWAYS hurts performance due to nofold semantics (forced copies prevent optimization)
- tile+promotion+vec (M4) = 20.018 ms — catastrophic, nofold copies inside 3 nested loops
- fusion→promotion→vec (M5) = 1.414 ms — nofold on each 16x16/16x32 tile (4096 tasks × 3 copies)
- promotion→fusion→vec (M6) = 1.156 ms — nofold on full matrices once is less bad than per-tile
- Promotion before fusion (1.156) slightly better than after (1.414): 3 full-matrix copies vs 12288 tile copies
- **Conclusion**: Promotion is strictly inferior to padding in all tested contexts

### 11c. Peeling
| # | Schedule | Time (ms) | Speedup | Speedup to PyTorch |

| M7 | tile(16,32,24)->peel(back)->pad(8)->vec(4,8,8) | 7.657 | 11.06x | 0.025x |

**Peeling observations:**
- Peeling only applies when tile sizes don't evenly divide dimensions (e.g., K=24 into 256: 10×24 + 16 remainder)
- tile(32,32,32)->peel fails postcondition: 32 divides 256/512 evenly, nothing to peel
- Peeling splits K-loop into main (0..240 step 24) + remainder (240..256), padding makes each body vectorizable
- Without parallelism, the result (7.657 ms) is useless — sequential loops dominate
- fusion->peeling fails postcondition (from Phase 10): scf.forall incompatible with peeling
- **Conclusion**: Peeling is compositionally useful (works with pad+vec) but only relevant for non-dividing tile sizes, and still requires parallelism to be competitive

### Phase 11 Key Findings
- **Multi-level tiling cannot beat fusion**: Fusion's 3D task parallelism (scf.forall with 3D grid) is strictly superior to par(1D) + sequential tiled loops. The overhead of extra loop nests negates any cache benefit.
- **Promotion is always harmful**: nofold padding forces copies that the compiler cannot optimize away. Regular padding (without nofold) is strictly better in all tested contexts.
- **Peeling works compositionally but needs parallelism**: peel+pad+vec correctly handles non-divisible tile sizes, but without parallel execution, it's too slow. Since fusion→peeling fails postcondition, peeling cannot benefit from the best parallel pattern.
- **Best schedule unchanged**: fusion(16,32,16)->pad(8)->vec(4,8,8) = 0.327 ms remains optimal
