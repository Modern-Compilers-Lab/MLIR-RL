## Phase 3: Multi-Step Schedules (on 3 representative kernels)

### Chain A: Tiling[32,32,32] → VecPar[4,4,4]

All 3 kernels: Tiling Pre=T, Post=T; VecPar Pre=T, Post=T. Chain composes.

| Kernel | Time (ms) | Speedup vs base | vs PyTorch |
|--------|-----------|----------------|------------|
| matmul_128_128_128 | 4.92 | 0.54x | 0.017x |
| matmul_512_256_256 | 78.71 | 1.06x | 0.002x |
| matmul_2048_256_512 | 626.84 | 0.55x | 0.001x |

**Verdict**: Tiling→VecPar is WORSE than base for small/large kernels. The nested scf.for + scf.forall creates excessive overhead. Not a viable schedule shape.

### Chain B: Packing[32,32,32] → VecPar

Packing transforms matmul (3 dims) into linalg.generic (6 dims). VecPar with 6-dim vector_sizes [4,4,4,4,4,4] fails precondition (Pre=F). VecPar with 3-dim vector_sizes [4,4,4] passed in Phase 2 compositional testing but produces structurally different output. **Not a reliable multi-step chain** due to parameter dimension mismatch.

### Chain C: ParTile[32,0,0] → VecPar[4,4,4]

All 3 kernels: ParTile Pre=T, Post=T; VecPar Pre=T, Post=T. Chain composes cleanly with nested scf.forall (outer=ParTile distribution, inner=VecPar vectorization).

| Kernel | Time (ms) | Speedup vs base | vs PyTorch |
|--------|-----------|----------------|------------|
| matmul_128_128_128 | 0.20 | 13.2x | 0.43x |
| matmul_512_256_256 | 0.86 | 97.1x | 0.23x |
| matmul_2048_256_512 | 2.90 | 118.8x | 0.25x |

**Verdict**: ParTile→VecPar is viable but WORSE than standalone VecPar across all sizes. The outer ParTile distribution adds overhead that counteracts VecPar's inherent parallelism.

## Phase 4: Best Schedule Shape per Kernel Subset

### Summary Table

| Kernel Size | Best Schedule | Time (ms) | Speedup vs base | vs PyTorch |
|------------|--------------|-----------|----------------|------------|
| Small (128×128) | VecPar | 0.12 | 22.0x | 0.72x |
| Medium (512×256) | VecPar | 0.54 | 154.7x | 2.76x |
| Large (2048×512) | VecPar | 2.23 | 154.5x | 3.12x |
| Phase 1 ref (512×128) | VecPar | 0.44 | 187.8x | 1.74x |

### Conclusions

1. **VecPar is universally dominant** for matmul. No multi-step schedule improves upon it. This is because VecPar converts the entire matmul into a single scf.forall with vector operations, achieving full parallelism + vectorization in one step.

2. **Multi-step chains add overhead without benefit**:
   - Tiling→VecPar: Nested loops (scf.for → scf.forall) destroy performance
   - ParTile→VecPar: Double-nested forall creates scheduling overhead
   - Packing→VecPar: Dimension mismatch makes parameterization unreliable

3. **Recommended schedule shapes for RL policy**:
   - **Primary**: `[VecPar]` — single action, always best
   - **Fallback 1**: `[ParTile, Tiling, VecPar]` — canonical HPC 3-step (distribute→tile→vectorize); 132.6x on medium, gap narrows to 1.10x vs VecPar at large sizes
   - **Fallback 2**: `[ParTile, VecPar]` — 2-step parallel+vectorize; 118.8x on large
   - **Fallback 3**: `[Tiling, VecPar]` — cache-tiling + vectorize; structurally sound, RL tunes tile sizes
   - **Sequential**: `[VecSeq]` — 7.57x; useful when parallelism is constrained

4. **Terminal constraint is absolute**: VecPar and VecSeq must always be the LAST action in any schedule. No recovery is possible after vectorization.

### Cross-Kernel Validation: ParTile(2D)→Tiling→VecPar

Parameters: ParTile[64,64,0] → Tiling[32,32,32] → VecPar[4,4,4]. All 3 kernels: all steps Pre=T, Post=T.

| Kernel | VecPar alone (ms) | PT→T→VP (ms) | Speedup vs base | Gap vs VecPar |
|--------|-------------------|---------------|----------------|---------------|
| matmul_128_128_128 | 0.12 | 0.20 | 13.2x | 1.67x slower |
| matmul_512_256_256 | 0.54 | 0.63 | 132.6x | 1.17x slower |
| matmul_2048_256_512 | 2.23 | 2.45 | 140.7x | 1.10x slower |

**Verdict**: ParTile→Tiling→VecPar is the strongest multi-step chain discovered. The gap with standalone VecPar narrows as kernel size increases (1.67x → 1.17x → 1.10x), suggesting that at very large sizes the explicit work distribution may match or beat VecPar. Included in SCHEDULE_GRAPH as a structurally distinct 3-step path for RL parameter optimization.

### Dead Ends

- **Tiling→Tiling→VecPar**: Double tiling creates deeply nested scf.for loops → 627.4ms (0.13x), catastrophic overhead.
- **Tiling(large)→VecPar**: Single large-tile tiling [64,64,64] + VecPar achieves only 8.36x — the scf.for nesting from tiling interferes with VecPar's parallelism.

## Extended Exploration: VecSeq Mirror Chains (on matmul_512_256_256)

All 3 VecSeq mirror chains validated: Pre=T, Post=T at every step.

| Schedule Shape | Probe Parameters | Time (ms) | Speedup vs base |
|---------------|-----------------|-----------|----------------|
| ParTile→VecSeq | [64,64,0]→[4,4,4] | 0.93 | 89.8x |

| ParTile→Tiling→VecSeq | [64,64,0]→[32,32,32]→[4,4,4] | 0.59 | 141.6x |

**Key finding**: ParTile→Tiling→VecSeq (0.59ms) **beats** the VecPar equivalent ParTile→Tiling→VecPar (0.63ms). The ParTile scf.forall provides parallelism, and VecSeq adds vectorization within each tile as scf.for loops — avoiding a nested parallel construct. This makes the VecSeq 3-step chain the fastest multi-step schedule discovered.
