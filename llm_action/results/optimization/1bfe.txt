### 1. `transform.structured.tile_using_for`

This operation tiles a linalg operation using `scf.for` loops. The key return values are:

## Answer

1. **`tile_using_for` returns loop handles directly**: The `tile_using_for` operation already provides handles to the generated loops via its second result (`loops`). There is no need to separately match or extract loop handles afterward.

2. **Use the `interchange` attribute on `tile_using_for` itself**: Apply loop reordering **during tiling**, not after, by specifying the optional `interchange` attribute. This is more efficient and correct.

3. **If interchange is needed after tiling**: Use `transform.loop.interchange` on the returned loop handles from `tile_using_for`. However, detailed semantics for this operation are minimally documented; prefer using the built-in `interchange` parameter of `tile_using_for`.

4. **Loop handle typing**: The `loops` result is a variadic of `TransformHandleTypeInterface` instances—one handle per non-zero tile size dimension.

5. **Precondition**: The operation only works on `LinalgOps`. Ensure your target operation is linalg-based (e.g., `linalg.matmul`, `linalg.generic`).

6. **Static vs. dynamic tile sizes**: Tile sizes can be static (in `static_sizes` attribute, with 0 meaning "don't tile this dimension") or dynamic (passed as operand handles). Use 0 for dimensions you don't want to tile.

## Constraints / Preconditions

- **Target must be a `LinalgOp`**: Operations like `linalg.matmul`, `linalg.generic`, `linalg.convolution`. Non-linalg ops cause silenceable failure.
- **Interchange attribute**: A `DenseI64ArrayAttr` specifying the permutation of loop dimensions. Length must match the number of non-zero tile sizes.
- **Loop handles are co-indexed**: If you return `N` loop handles, they correspond to the `N` non-zero tile sizes in left-to-right order.
- **Perfect loop nest assumption (if using `transform.loop.interchange` afterward)**: The loop nest must be perfectly nested for standalone `interchange` to work reliably.
- **Dynamic tile sizes must match list length**: If using `dynamic_sizes` operands, the number of handles must match the count of `ShapedType::kDynamic` values in `static_sizes`.

- **Speedup**: **19.90×**

### Key Optimization Insights

1. **Multi-level tiling was critical**: Single-level tiling achieved only ~7× speedup, while two-level tiling enables better register reuse
2. **Smaller vectors won**: `vector<4x8xf64>` and `vector<8x8xf64>` (32-64 elements) outperformed larger `vector<16x16xf64>` (256 elements), likely due to better register allocation and reduced spill
3. **Loop interchange hurt performance**: The default memory access pattern was already optimal for this kernel
4. **Unrolling added overhead**: The vectorized code already had good instruction-level parallelism
