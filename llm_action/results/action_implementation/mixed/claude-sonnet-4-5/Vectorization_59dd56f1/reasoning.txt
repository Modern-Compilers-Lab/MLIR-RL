## Answer

1. **Primary operation for linalg vectorization**: `transform.structured.vectorize`
   - Use this when you want fine-grained control over a single linalg op or set of ops
   - Supports both regular (inferred) and masked (explicit vector sizes) vectorization

2. **For vectorizing nested children**: `transform.structured.vectorize_children_and_apply_patterns`
   - Use this when the target is a higher-level op containing multiple linalg ops

3. **Required operand**: `target` handle

   - Type: `TransformHandleTypeInterface` / `!transform.any_op`

4. **Vector sizes parameter** (optional):

## Revised Strategy

The issue is that vectorizing a high-level linalg operation without prior tiling will attempt to vectorize the entire operation, creating unrealistic vectors. There are two approaches:

1. **Require prior tiling**: Make the precondition check that the operation has already been tiled to small tile sizes
2. **Use explicit vector sizes**: Provide conservative vector width parameters

For an RL environment where actions must be composable and may be applied in various orders, **Option 1 is more robust**. The action should:
- Check if the operation is "vectorization-ready" (i.e., has been tiled to small sizes)
- Only apply vectorization if the operation is already in a vectorizable form

However, this creates a circular dependency: we need to know the loop structure to determine if it's vectorization-ready.

**Alternative approach**: Use **explicit conservative vector sizes** that match AVX2 capabilities:
- For f64: vector width of 4 (matching 256-bit AVX2 register)
- For f32: vector width of 8

## Revised Understanding

The Transform dialect's vectorization is designed to work on **already-tiled operations** where the tile sizes are small enough to fit in vectors. The typical workflow is:

1. **Tile** the operation to small tiles (e.g., 4×4 or 8×8)
2. **Vectorize** the tiled operation (which now has small iteration spaces)

For an RL action space, this means:
- **Vectorization should be a late-stage action** that assumes prior tiling
- The precondition must check that the operation is in a vectorizable form
- OR: Vectorization should be combined with tiling in a single action

Given the constraints, I'll design the action as follows:

**Approach**: Use inferred vectorization, but make the **postcondition strictly enforce vector size limits**. If the vectorization produces oversized vectors, the postcondition returns False, treating it as "not applicable".

- The action will **succeed** on tiled operations (which have small iteration spaces)
- The action will **fail** (postcondition False) on untiled operations (which produce huge vectors)
- This makes it naturally composable: it only succeeds when applied after tiling

## Critical Realization

The Transform dialect's `vectorize` operation for matmul creates **rank-3 vectors** to represent the outer product + reduction pattern. This is mathematically correct but not hardware-realistic for AVX2.

The issue is fundamental: **matmul vectorization requires special handling** because it involves a reduction. MLIR's vectorizer creates `vector<MxNxK>` to represent the full computation, which then needs to be lowered to actual SIMD operations.

## Final Strategy: Strict Safety-First Approach

The fundamental issue is clear: **MLIR's inferred vectorization on high-level linalg ops creates tile-as-vector artifacts** that are not hardware-realistic.

For the RL action to be useful and safe, I need to:

1. **Accept that inferred vectorization is too aggressive**
2. **Make the postcondition strictly enforce vector size limits**
3. **Document that this action only succeeds on appropriately-tiled operations**

The action will:
- Apply inferred vectorization
- Check resulting vector sizes in postcondition
- **Fail (return False) if vectors exceed safety limits**

This makes it a **conditional action** that naturally composes with tiling: it only succeeds when the operation has been tiled to appropriately small sizes first.

Let me implement this design:

```python
from llm_action.src.actions.base import ActionBase
from llm_action.src.utils.transformation import run_transform_code
import re

class VectorizationAction(ActionBase):
    
    @classmethod
    def parameters(cls) -> dict:
        return {
            "vectorize": {
                "type": "bool",
                "default": True,
                "description": "Whether to apply vectorization (must be True for action to apply)"
            }
        }
    
    @classmethod
    def precondition(cls, code: str, params: dict) -> bool:
        """Check if vectorization should be attempted."""
        # Must be enabled
        if not params.get("vectorize", True):
            return False
        
        # Must have the required tag
        if 'tag = "operation_0"' not in code:
            return False
        
        # Basic sanity: must contain a linalg operation
        if "linalg." not in code:
            return False
        
        return True
    
    @classmethod
    def preprocess(cls, code: str, params: dict) -> str:
        """No preprocessing needed."""
        return code
    
    @classmethod
    def implement(cls, code: str, params: dict) -> str:
        """Apply vectorization using Transform dialect."""
        transform_code = (
            'module attributes {transform.with_named_sequence} {\n'
            '  transform.named_sequence @__transform_main(%arg1: !transform.any_op {transform.readonly}) {\n'
            '    %matched = transform.structured.match attributes{tag = "operation_0"} in %arg1 : (!transform.any_op) -> !transform.any_op\n'
            '    transform.structured.vectorize %matched : !transform.any_op\n'
            '    transform.yield\n'
            '  }\n'
            '}\n'
        )
        
        try:
            return run_transform_code(code, transform_code)
        except Exception:
            # If transform fails, return original code (postcondition will catch it)
            return code
    
    @classmethod
    def postcondition(cls, before: str, after: str, params: dict) -> bool:
        """Verify vectorization succeeded and produced safe vectors."""
        # Must have changed the IR
        if after.strip() == before.strip():
            return False
        
        # Basic sanity checks
        if not after or "func.func" not in after:
            return False
        
        # Vectorization safety check: scan for vector types and validate sizes
        vector_pattern = r'vector<([^>]+)>'
        vectors = re.findall(vector_pattern, after)
        
        for vec_spec in vectors:
            # Parse vector dimensions and element type
            # Format: "4x8xf32" or "16xi64" etc.
            parts = vec_spec.replace('x', ' ').split()
            if not parts:
                continue
            
            # Last part is the element type
            elem_type = parts[-1]
            
            # Earlier parts are dimensions (if any)
            dims = []
            for p in parts[:-1]:
                if p.isdigit():
                    dims.append(int(p))
            
            # Calculate total element count
            if dims:
                total_elements = 1
                for d in dims:
                    total_elements *= d
                
                # Determine limit based on element type
                if 'f64' in elem_type or 'i64' in elem_type:
                    limit = 16
                elif 'f32' in elem_type or 'i32' in elem_type:
                    limit = 32
                elif 'f16' in elem_type or 'bf16' in elem_type or 'i16' in elem_type:
                    limit = 64
                elif 'i8' in elem_type:
                    limit = 128
                else:
                    # Unknown type, use conservative limit
                    limit = 16
                
                # Check if exceeds limit
                if total_elements > limit:
                    return False
                
                # Check rank (prefer rank-1, allow small rank-2/3, reject rank>=4)
                rank = len(dims)
                if rank >= 4:
                    return False
                
                # For rank-3, be extra conservative
                if rank == 3 and total_elements > limit // 2:
                    return False
        
        return True
```

## Final Understanding

After extensive testing, I now understand the constraints:

1. **Linalg vectorization creates vectors matching the iteration space rank**
2. **High-rank vectors (≥4) fail in the lowering pipeline**
3. **Even small high-rank vectors fail to execute**
4. **Rank-3 vectors with reduction (matmul pattern) fail to execute**

This means **direct vectorization of linalg ops is not viable for this action** without additional lowering support.
